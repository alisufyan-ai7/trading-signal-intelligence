# EXP-2026-056 — Proposed GFS retention for encrypted S02 dual-cloud backups (DESIGN ONLY)

Date: 2026-10-24 | Status: **PROPOSED; NO DELETION OR ACTIVE RETENTION** | Scope: Issue #67 / existing draft PR #85 | Repo: `alisufyan-ai7/trading-signal-intelligence`.

## Owner request and motivation

Owner wants the last 30 days of daily backups, a lower-frequency weekly or monthly recovery point for older history, and advice on best practices. First manually verified real dual-cloud backup, `backup-8bce80179c524ace8f4a52cb702b3716`, and first real scheduled verified dual-cloud backup, `backup-83688210120f48fa8dd62491720df132`, have succeeded and must be preserved. The installed daily scheduler runs 04:15 VPS-local time (observed UTC+00), uses immutable unique backup IDs, saves encrypted data and encrypted recovery receipts to AWS S3 and Backblaze B2, retains a local encrypted receipt, independently restores from each cloud, and currently performs **no deletion**. These are source/evidence observations within this repo.

This is a **policy recommendation**, not a request or authorization to grant deletion IAM permissions, install a cleanup task, change bucket lifecycle policies, or remove any objects.

## Recommended grandfather-father-son (GFS) recovery points

- **Daily:** keep every successful, independently dual-cloud-verified backup for the trailing **30 complete UTC days**.
- **Weekly:** for the subsequent **60 days** (ages >30 and <=90), retain **one most recent verified backup for each distinct ISO UTC week**. Expect ~8–9 weekly points depending on date boundaries.
- **Monthly:** for verified backups older than 90 days, retain **one most recent verified backup per UTC calendar month**, covering the **previous 12 months of this older tier** (nominally extends protection to approximately 15 months). If a month has no valid backup, surface a coverage gap rather than falsely claiming a monthly point exists.
- **Special pins:** preserve owner-pinned milestones, disaster recovery drills and earliest first real manual backup `backup-8bce80179c524ace8f4a52cb702b3716` until separately approved to unpin. Never expire the newest TWO distinct independently restorable dual-cloud recovery points irrespective of age, especially during outages.
- **Bound:** approximately **30 daily + 8/9 weekly + up to 12 monthly = ~50–51 ordinary snapshots/provider** after maturation, plus manually pinned items. A recovery point consists of BOTH encrypted data objects (one per cloud), BOTH encrypted cloud manifests, and available private encrypted local receipt. Exact number varies by overlapping boundaries, missing runs, duplicate time buckets and pinned history.
- **Time basis:** use UTC from independently attested successful completion timestamps, NOT object filename generation or local modified timestamp. Calculate tiers at one fixed `as_of_utc`; account for clock skew, overdue runs and overlapping weeks/months. Never promote an unverified or partial backup into an otherwise missing weekly/monthly slot.
- **Backup frequency remains daily.** Retention is a *subsequent independent review/purge workflow*, not a strategy of backing up only weekly/monthly. Monthly records are selected from previously successful daily captures.
- **Cadence for eventual cleanup:** daily dry-run candidate planning, at most weekly destructive purge after a minimum 7-day owner-visible grace period. No automatic deletion within the first onboarding window.

## Mandatory safe-pruning conditions (fail closed)

1. **Immutable verified inventory:** consolidate owner-only successful `history.jsonl` with an authoritative nonsecret inventory for the original manual backup and *exact version IDs* of all data+manifest objects in AWS and Backblaze. The current scheduled JSONL records `backup_id`, `at_utc`, record count and pass status but NOT each exact cloud `VersionId`; the encryption receipt manifest stores data object version IDs but does not record the encrypted *manifest's* own cloud version IDs. Cloud version inventory will require read-only permissions/capabilities beyond current role assumptions. Never infer existence, success or provider version ID from a backup ID alone.
2. **Recoverability gate:** candidate eligible for retention only if exact encrypted data+manifest are present and decryptable with owner-held passphrase from BOTH providers and the SQLite restore/integrity check PASS; a stored object without an intact matching manifest is not a recoverable snapshot. Do not treat a successful prior-day restore as a guarantee that versions still exist.
3. **Cross-provider concordance:** preview exact backup IDs, AWS data+manifest version IDs, B2 data+manifest version IDs, byte hashes, retained weekly/monthly representatives and deletion candidates. Refuse cleanup on disagreement, access-denied, missing inventory, orphaned ciphertext/manifest, legal hold/object lock, failed job or `operator-review-required.json` latch.
4. **Freeze independent protections:** protect last two verified recovery IDs and the original manual baseline; never delete both provider copies or manifests for any protected ID. Prefer keeping a recent one immutable/object-locked for short ransomware resistance, but account for object-lock support, expiration and additional costs before enabling; no new bucket config or IAM changes under this design.
5. **Separate delete authority:** current four backup principals are writer/reader only and should remain unable to delete older data. A tightly scoped, separately approved delete operator (never the daily backup task) with explicit version-aware rights, maker-checker/owner approval, and an audit trail is required. Avoid broad S3 bucket lifecycle rules that might purge historical pinned backups or erase noncurrent versions invisible to ordinary GET requests.
6. **Grace and evidence:** generate a human-readable dry-run, retain the approved candidate plan for >=7 UTC days, then re-evaluate immediately before deletion. Never automatically act on stale manifests, ambiguous partial uploads, failed data integrity or a missing retained period. After each selective purge, verify that every retained provider manifest+data copy remains restorable. Record statuses and timestamps with no secrets or decrypted data.
7. **Version-correct cleanup:** delete exact intended historical object versions and, when appropriate, delete markers; AWS and B2 have version-related semantics requiring per-provider API compatibility verification. A plain non-versioned DeleteObject without explicit version can create a delete marker rather than free storage, and a cloud lifecycle policy might delete versions that must be pinned. Both encrypted data objects and both encrypted receipts must be handled as a reconciled recovery point. Do NOT purge local recovery receipts until retained cloud manifests and off-VPS secret custody are confirmed.
8. **Ransomware/rights:** daily backups currently have cloud copies but shared VPS context can access credentials and scheduled passphrase. Use least privilege, separate deletion authority and protected offsite custody; more historic backups are useless if an attacker with common delete privilege can purge all copies. Cloud costs and restore API request fees accumulate with every daily verification; revisit policy when objects/data grow.
9. **Stop-on-failure:** block retention on recent unacknowledged backup failures, the scheduler's incident latch, coverage gaps, provider disagreement, anomalous growth or any test restoration failing. Have a manual recovery checklist for reconciliation.

## Current implementation: no cloud deletions

Existing code `manual_dual_cloud_backup_v0_1.py` and `vowsig_s02_automatic_backup_v0_1.py` has no delete API; both providers store one new object+manifest per unique ID. Successful automated records explicitly set `older_cloud_versions_deleted=false`. Neither `VersionId` inventories for manifest objects nor an authorized expirer exist in current PR. The current daily scheduled task MUST remain unchanged and continue preserving old objects while this retention plan is reviewed. The initial backup database size was small (30 records); current storage savings from destructive pruning are likely modest compared with the impact of accidental loss. No actual dollar amount or external provider feature claim was verified in this design-only document.

## Owner-facing decision

**Recommended default:** 30 daily / ~8 weekly / 12 monthly / special-pinned initial backup + two recent recovery points / seven-day grace / read-only dry-run first. Keep existing task running. Do not enable auto-deletion until the versioned two-provider inventory, safe IAM separation, recovery-gated planner, and owner-reviewed deletion controller are independently validated. This requested recommendation is not authorization to delete.

Alternative low-risk first step: permanently keep all backups until the first 30 days of reliable scheduled data exist and cloud billing is measured; then consider implementing the above conservative algorithm.
