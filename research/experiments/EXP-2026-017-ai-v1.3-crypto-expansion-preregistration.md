## Research objective

Create a new, separately governed prospective crypto shadow lineage for VowSig
without changing, restarting, pooling with, or contaminating the active AI-v1.1
and AI-v1.2.1 lineages.

The frozen initial crypto cohort is:

1. BTCUSDT — BTC/USDT
2. ETHUSDT — ETH/USDT
3. SOLUSDT — SOL/USDT

Working runtime/evidence identity:

`AI-v1.3`

`crypto-expansion-1`

`AI-v1.0`

The runtime/version distinction is required because the data source, 24/7 calendar,
volume semantics and execution-cost semantics differ from the active

remains unchanged.

## Why these three markets

### BTCUSDT

BTCUSDT is the primary crypto benchmark and already has an explicit Binance Spot
canonical mapping in the repository. The existing cross-source audit also
defaults to BTCUSDT and can compare Binance Spot against the distinct Exness
BTCUSDT CFD for read-only sanity checking without treating the feeds as
interchangeable.

### ETHUSDT

ETHUSDT adds a second major crypto market and tests whether the decision system
generalizes beyond BTC while remaining within a highly liquid, mature crypto
market family.

### SOLUSDT

SOLUSDT adds a materially higher-beta crypto market and is intentionally retained
as a stress case for volatility/regime transfer. It must not be dropped after
performance-bearing evidence begins because early results are weak.

## Deferred crypto markets

All other crypto markets are deferred from the first cohort.

No XRP, BNB, DOGE, ADA or other crypto may be substituted into this cohort after
performance-bearing activation merely because BTC / ETH / SOL results are weak,
low-activity or operationally inconvenient.

A later cohort requires a separately preregistered expansion decision.

## Feature protocol

The crypto runtime intends to preserve the existing formulas for:

- ret_1 / ret_4 / ret_12 / ret_24;
- Wilder ATR(14);
- ATR percentile;
- H1/H4 EMA20/EMA50 state and slopes;
- Wilder RSI(14);
- prior-20 structure;
- previous UTC-day structure;
- true-range expansion;
- realized-volatility regime;
- deterministic trend regime;
- return-sign agreement;
- fixed UTC descriptive session bucket;
- UTC hour and day-of-week.

However, the current `AI-v1.0` feature definition is not semantically identical
for crypto because it defines volume as MT5 tick volume and requires a completed
H1 spread field.

Therefore the crypto feature profile must be separately versioned before any
performance-bearing provider call.

Working feature-schema version:

`AI-crypto-v1.0`

### Crypto volume semantics

`volume_z_20` may retain the same z-score formula, but its underlying observation
for the crypto profile is Binance Spot base-asset volume.

The crypto schema/activation bundle must bind this exact semantic definition.

The runtime must not claim that Binance base-asset volume is MT5 tick volume.

### Session semantics

The existing ASIA / LONDON / NEW_YORK / LATE UTC buckets may be retained only as
descriptive fixed UTC buckets. They are not exchange-open/session-open claims for
a 24/7 market.

`utc_day_of_week` remains part of the snapshot.

Gate reports must separately decompose weekday and weekend outcomes.

### Spread / execution context blocker

The current Binance kline adapter intentionally sets:

`spread=None`

The active AI-v1 feature builder requires a finite spread and explicitly treats
missing spread as invalid.

Therefore the crypto protocol forbids all of the following:

- substituting spread=0;
- reusing an unrelated MT5 spread;
- inferring spread from H1 high/low;
- silently dropping the cost feature;
- treating Binance kline OHLC as bid/ask data.

Before activation, implementation must add a prospective read-only Binance
top-of-book observation path for the decision point.

Working semantic intent:

- capture best bid and best ask prospectively;
- `spread_price = best_ask - best_bid`;
- record source and observation timestamp;
- require finite non-negative spread;
- reject/fail closed if unavailable;
- bind the exact implementation and schema before activation.

This prospective top-of-book context may not be reconstructed after the fact for
missed live opportunities.

## Execution-cost protocol blocker

The current active AI cost rule is based on a spread-derived cost multiplier.

Crypto Spot needs an all-in research cost model that accounts for at least:

- bid/ask spread;
- transaction fee assumptions;
- a preregistered slippage buffer or explicit zero-slippage research assumption.

The exact numerical crypto fee/slippage policy is deliberately NOT invented in
this design package because the current repository does not contain an admitted
canonical fee schedule/calibration for BTCUSDT / ETHUSDT / SOLUSDT.

This is a hard activation blocker.

Before activation, the owner-reviewed readiness package must freeze:

1. fee-rate source and exact rate per side;
2. slippage-buffer rule;
3. all-in round-trip cost formula;
4. guard threshold interaction;
5. lifecycle cost allocation across TP1/TP2/STOP/TIMEOUT;
6. source/hash/version of every cost parameter.

The machine-readable design config therefore leaves those numeric fields null and
sets:

`activation_blocked_until_numeric_cost_policy_frozen = true`

No performance-bearing crypto inference is admissible before that blocker is
closed prospectively.

## Cadence and scheduler design

Decision opportunity:

- each completed H1 bar;
- 24 hours/day;
- 7 days/week.

Working scheduler target:

- near UTC minute 04 after the completed H1 boundary.

Reason:

- active AI-v1.1 runs near :02;
- active AI-v1.2.1 runs near :03;
- crypto receives a separate offset;
- product publication remains independently governed.

The crypto runtime must build/freeze the causally available feature/execution
snapshots for all three crypto markets before beginning provider calls for the
batch. This prevents later markets in a sequential provider loop from receiving a
different feature timestamp merely because earlier provider calls took longer.

The existing 300-second maximum data-age intent is retained in the design. If
readiness proves that :04 plus bounded synchronization cannot satisfy it
reliably, the scheduler/latency design must be corrected before activation; the
freshness threshold may not be relaxed post hoc after performance is observed.

No scheduler is installed by this preregistration.
