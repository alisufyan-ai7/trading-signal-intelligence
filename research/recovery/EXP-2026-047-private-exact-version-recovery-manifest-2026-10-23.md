## Genuine disaster-recovery gap

P2's successful `_one_provider` returns a `version_sha256` only. Hashing AWS/B2 S3 `VersionId` is good for sanitized logs but *not reversible*. Without saving the exact opaque version identifiers privately, an operator cannot reliably issue the `GET` for each verified immutable version during a later host/region disaster. An in-memory version variable that vanishes after the invocation is not a durable recovery plan.

## Proposed offline component

`src/trading_signal_intelligence/recovery/private_versioned_restore_manifest_v0_1.py` introduces two independently held keys: the real-data AES-256-GCM key and a distinct AES-256-GCM key for the **private manifest**. The manifest is constructed only after accepting a P2 result with exactly five signed request events and two verified provider receipts. It checks provider name/region/object SHA/record count and compares each supplied opaque *exact* version ID's hash against the sanitized P2 result. Exact IDs, bucket, region, object key and immutable data identity are then stored solely within a fresh-nonce authenticated encrypted manifest. Private dataclass representations explicitly redact ciphertext bytes, object keys, and both raw provider VersionIds to prevent routine object logging from leaking recovery references. No plaintext version IDs are printed or returned in the public summary. An independent offline opener verifies AES-GCM authenticity, exact schema, provider pins, object key/sha binding and version field format. This code never accesses an SDK, source SQLite, files, network, credentials or scheduler on import or execution.

**Important limitations:** This module does NOT yet capture VersionIds from P2; P2 currently discards those raw IDs after hashing. A future reviewed P2/operator integration needs an explicit private receipt sink, with **no raw version IDs in public logs or GitHub**. The standalone method accepts caller-provided raw IDs and verifies only that they hash to the P2 receipts. It cannot independently establish that an S3 object exists or is retained, that credentials are recoverable, or that source rights and billing are valid. A cryptographically correct manifest is not real offsite disaster-recovery proof.

**Storage and custody:** The module deliberately returns encrypted bytes, and does not claim durable off-host persistence. A future operator must place them exclusively in owner-controlled private, independent storage with actual ACL checks, backup/restore drills and no-overwrite semantics; it must preserve the **separate manifest decryption key**, real-data encryption key and scoped cloud reader identities off VPS. Neither version IDs nor keys belong in GitHub or public telemetry. A manifest lost with the VPS defeats exact-version recovery; a lost encryption key defeats data recovery.
